# Toward a proof-carrying semantic compiler

**Date:** 2026-11-21  
**Status:** architecture synthesis and research target; not a completed system or novelty claim  
**Related:** DAP_RESOURCE_INDEXED_OBSERVATIONAL_CONGRUENCE.md; ULTIMATE_RESEARCH_CAMPAIGN_2026-11-21.md

## 1. The actual culmination target

The long-term objective is a system that can take a formalized representation, identify which distinctions matter to a declared task, derive a sufficient abstraction, generate alternative realizations, and adopt an improvement only when a small trusted checker verifies the required semantic and resource contracts.

The intended universality is an interface and certificate discipline that can be instantiated across different formal domains. It is not a claim that one finite algorithm can decide arbitrary semantic importance, prove every mathematical truth, or discover the user's values without a specification.

The core loop is:

1. **Specify:** declare the domain, observations, operations, admissible contexts, resource model, provenance requirements, and allowed losses.
2. **Model:** interpret the source in an appropriate semantics (truth tables, transition systems, algebraic models, proof objects, or a domain-specific model).
3. **Abstract:** compute or propose a coarser representation that preserves the protected contextual behavior.
4. **Realize:** generate candidate representations or algorithms in alternative substrates.
5. **Certify:** produce evidence for observation preservation, operation compatibility, resource admissibility, and provenance/loss obligations.
6. **Check:** independently verify certificates in a small trusted kernel.
7. **Optimize:** compare only verified candidates using explicit cost and fidelity dimensions.
8. **Record:** attach the result, assumptions, trust base, and dependencies to the claims ledger.
9. **Compose:** reuse certificates across modules and transformation pipelines only when intermediate contracts match.

## 2. A typed representation model

A representation module M is proposed to contain:

- a family of carriers/states S, possibly many-sorted;
- a typed signature Σ of operations and relations;
- a family Q of protected observations;
- a class C of admissible contexts generated by protected operations;
- a resource algebra R and an admissibility relation for context/environment usage;
- a data-provenance domain P;
- an action-provenance domain A;
- an explicit loss policy L;
- a module interface describing which structures may be imported, exported, restricted, or abstracted.

The components are separate on purpose. State identity, formula/type identity, occurrence identity, provenance, and phenomenal or observational identity must not be conflated.

## 3. Task-relative semantic quotient

For a state x in S, define its protected contextual behavior as the family of all observations of C[x], for every well-typed resource-admissible context C in C and every compatible observation q in Q.

Define x ≈M y when these contextual behaviors agree.

Under the appropriate closure conditions on C, this is an observational congruence. Quotienting S by ≈M gives the coarsest representation that identifies no two states distinguishable by a permitted context and protected observation.

This is a task-relative canonical abstraction:
- it removes distinctions irrelevant to the declared observation/context protocol;
- it preserves distinctions that some permitted continuation can reveal;
- it changes when Q, C, or R changes;
- it does not determine which observations should matter in the first place.

The construction is standard in the tradition of contextual equivalence and behavioral quotienting. The research question is whether the resource, provenance, and module-indexed obligations can be integrated into a useful certified abstraction procedure beyond existing frameworks.

## 4. Transformation certificate

For a transformation T : M → N, a certificate should carry independent, checkable obligations:

| Component | Obligation |
|---|---|
| Observation | Protected observations factor through T or are preserved up to a declared relation |
| Operations | Protected operations commute with T or satisfy a simulation/bisimulation contract |
| Contexts | Admissible contexts are transported without silently expanding the observer's power |
| Resources | A usage-aware environment/linear map proves that source budgets cover target demands |
| Data lineage | Target occurrences record alternative and joint source dependencies |
| Action lineage | Fusion, splitting, erasure, reordering, and other transformation actions remain traceable |
| Loss | Every discarded distinction/observation/provenance detail is named and permitted |
| Assumptions | The checker records axioms, premises, and trusted components explicitly |

The certificate is not the transformation implementation. It is a proof object that a smaller checker can validate.

## 5. Composition

For M0 --T1--> M1 --T2--> M2, certificates compose only if:
- the output observation interface of T1 matches the input contract of T2;
- resource environments compose and their capacity side conditions hold;
- operation simulations are composable in the selected semantic category;
- data provenance annotations compose under the chosen provenance algebra;
- action-trace abstractions compose under a proved trace/bisimulation rule;
- losses are accumulated and never hidden;
- assumptions and trusted bases are joined monotonically.

The resulting certificate must prove the obligations for T2∘T1. Associativity and identity laws are desirable, but the relevant equivalence notion must be specified. In particular, weak bisimulation is not assumed to compose without side conditions.

Garchery's proof-carrying logical transformations already establish modular certificates with holes and composition for proof-task transformations. Wood–Atkey already establish composition of usage-aware environments. Green–Karvounarakis–Tannen already establish compositional data provenance. Dal Lago–Gavazzo establish full abstraction of resource transition systems for a linear effectful calculus. Tian–Liu give a close preprint comparator for action-reflective provenance across non-injective graph rewrites. The DAP system must build on these rather than rediscover them.

## 7. Concrete missing seams

### 7.1 Trusted resource kernel

Move P091's finite profile/context checks behind an independent checker, with a small artifact schema and no imports from the untrusted search layer. The checker should validate:
- unique occurrence tokens;
- exact token/profile correspondence;
- formula/rank alignment;
- nonnegative usage;
- linear per-token bounds;
- aggregate formula demand against capacity;
- provenance consistency;
- explicit rejection of persistent resources until their semantics is implemented.

The Python adapter can remain an untrusted constructor/search routine. Its output is accepted only if the kernel checks it.

### 7.2 Resource-aware LTS

The direct baseline is Dal Lago–Gavazzo's resource transition system: its state is not just a control state with a static budget, but a configuration carrying reusable resources and linear resources alongside the tested program. A finite Semplex version should therefore use configurations of the form:

`(control_state, reusable_pool, linear_pool)`.

A transition rule must specify:
- action label and control-state update;
- which linear tokens it consumes;
- which linear tokens it produces;
- which reusable resources it reads without consuming;
- whether a modality operation moves a reusable computation into the reusable pool;
- occurrence and action-provenance annotations;
- optional declared loss/action abstraction.

The untrusted explorer can enumerate the reachable configuration graph, with explicit bounds on states and resources. The trusted checker must verify **graph completeness**, not merely that every listed edge is legal: an untrusted explorer could otherwise omit an enabled transition and manufacture a false bisimulation. For a finite system, the kernel should recompute all enabled rule instances from each reachable configuration and compare the complete successor set with the artifact. Only then should kernel_lts check bisimulation/trace certificates on the extended states. P091 can initialize/check the finite all-linear part; persistent resources must remain out of scope until their modal semantics is justified.

The important research seam is **static/dynamic adequacy**: a C-20/QTT usage vector should act as a static budget or potential for the dynamic resource configuration. A candidate theorem says that every reachable execution trace consumes no more of each linear occurrence than its statically certified usage/capacity allows. P091 supplies the token-to-coordinate alignment; a resource-transition checker supplies the dynamic accounting. The exact statement must distinguish variable multiplicity, term usage grades, and resource availability. QTT's substitution theorem and Dal Lago–Gavazzo's resource operational semantics are the baselines. This is a formalization/integration target, not yet a novelty claim.

This is a project-specific implementation of an established resource-transition idea, not a new semantics claim.

### 7.3 Provenance upgrade

Replace flat concatenated origin tuples only if a concrete requirement demands it. Compare:
- provenance polynomials for alternative/joint data dependencies;
- action traces or coalgebraic observations for transformation history;
- a projection map to coarser views such as Boolean support or simple origin sets.

A more expressive provenance representation must be justified by counterexamples showing what the current tuple cannot preserve.

### 7.4 Certificate envelope and ledger connection

Define one artifact that references:
- source and target representation hashes;
- resource-check certificate;
- LTS/observational certificate;
- data/action provenance;
- loss declaration;
- assumptions and trust base;
- ledger claim IDs and dependency links.

A kernel_dap checker should validate each component and their compatibility. The ledger should record the resulting verdict using its existing warrant joins. It must not be possible to upgrade an untrusted result to KERNEL_CHECKED without an authentic verdict.

### 7.5 End-to-end optimizer

Generalize the F0 pipeline only after the certificate envelope works for F1/P091. The optimizer should:
- generate candidates with untrusted algorithms;
- reject out-of-scope or underspecified tasks;
- check fidelity and resource/provenance obligations;
- retain failed candidates with counterexamples;
- compare verified candidates on explicit cost dimensions;
- claim improvement only when fidelity is verified and the cost relation is satisfied.

## 8. Minimal vertical slice

The first useful end-to-end slice should be small and finite:

1. Build two finite LTS representations with the same protected observations but different internal states.
2. Give each transition a finite resource demand and source-origin label.
3. Construct a candidate quotient/translation that merges internal states.
4. Have untrusted code propose a bisimulation relation, resource profile, and provenance map.
5. Have kernel_lts and the new resource kernel independently check the evidence.
6. Compose the two subcertificates into a DAP certificate.
7. Record the result in Ledger with all assumptions and dependencies.
8. Add counterexamples where immediate trace equivalence passes but a protected context, resource limit, or provenance observer distinguishes the systems.

This slice tests whether the integration is substantive. If it merely bundles independent checks without a new soundness property or useful synthesis capability, call it an engineering integration rather than new mathematics.

## 9. Long-term theorem targets

1. **Contextual quotient soundness:** the quotient by resource-indexed observational congruence preserves all declared protected observations and operations.
2. **Resource certificate soundness:** a checked environment map implies target demand is covered by source capacity.
3. **Provenance soundness:** target data/action annotations correctly represent the allowed source dependencies and transformation history.
4. **Certificate composition:** compatible certificates compose to a sound certificate for the composite transformation.
5. **Module transport:** restriction, extension, and composition of module interfaces preserve or explicitly weaken certificates.
6. **Optimizer soundness:** every accepted improvement preserves the declared fidelity relation and satisfies the declared resource/loss contracts.
7. **Canonical abstraction:** the computed quotient is terminal among the declared admissible representations, with a precise universal property.

Each theorem must have a finite formal model first, then a generalized statement only if justified. Do not use “universal” as a substitute for an explicit domain and theorem.

## 10. Non-goals and truth conditions

The compiler cannot decide which goals are valuable without a supplied objective or preference model. It cannot prove that its semantic model is grounded in reality merely by proving transformations correct relative to that model. It cannot guarantee global optimality without lower bounds or exhaustive search. It cannot infer the correct protected observations from data alone without additional epistemic assumptions.

The system should make these limitations first-class rather than promise to eliminate them. Its strongest possible guarantee is conditional but rigorous: given a declared model, task, resource algebra, and trust base, every accepted transformation preserves the specified behavior and accounts for every permitted loss.

## 11. Optimality, monotonic improvement, and irreducible information

The semantic quotient and the implementation optimizer solve different problems and must not be conflated.

### 11.1 Semantic irreducibility

The quotient by resource-indexed contextual equivalence removes distinctions that no declared admissible context and protected observation can detect. Relative to the declared interface, this is the irreducible semantic content of the source representation.

It does **not** follow that:
- the quotient has the shortest encoding;
- the quotient is the fastest implementation;
- every remaining distinction is physically or metaphysically fundamental;
- the chosen observations capture every relevant aspect of reality.

A minimal sufficient semantic representation can still have a computationally expensive implementation.

### 11.2 Certified candidate optimization

Each candidate implementation should be represented by:
- a correctness/admissibility certificate;
- a cost vector, e.g. latency, throughput, memory, energy, code/model size, adaptation cost, and verification cost;
- a workload or instance distribution;
- a hardware/runtime context;
- measurement methodology and uncertainty.

Candidates that fail the semantic, resource, or provenance contracts are excluded before optimization. Among verified candidates, maintain a Pareto frontier. An incumbent may be replaced only when the new candidate dominates it under the declared objective or when the user explicitly accepts a trade-off.

This makes improvement monotonic relative to the declared cost order: the certified frontier should not regress. It does not imply that the globally optimal implementation has been found.

### 11.3 Lower bounds and optimality claims

A candidate may be called optimal only relative to:
1. a defined task and instance domain;
2. a cost model and hardware assumptions;
3. a search space or lower-bound theorem;
4. a proof that no candidate in the declared domain can do better.

If exhaustive search is infeasible, report “best verified candidate found” rather than “optimal.” If an information-theoretic or computational lower bound is known, attach its assumptions and proof to the certificate. The gap between candidate cost and the strongest valid lower bound is an explicit optimality gap.

The irreducible/reducible split is therefore two-layered:
- **semantic irreducibility:** what cannot be abstracted away without violating protected behavior;
- **computational irreducibility:** what cannot be reduced below a proven resource lower bound for the declared model and workload.

These notions are related but not identical. A representation can be semantically minimal and computationally inefficient; a clever implementation can reduce runtime without changing the semantic quotient.

### 11.4 Incremental search

The optimizer should preserve a verified incumbent and a provenance-rich candidate archive. New discoveries are evaluated against the same task, workload, and hardware contract. A candidate that improves one metric but worsens another remains on the Pareto frontier if neither dominates the other. The system must not silently change benchmarks, workloads, or cost weights to manufacture an improvement.

The existing F0 pipeline's Pareto-front and improvement-claim machinery is a starting point, but its finite Boolean cost model is not yet a general resource-aware optimizer.

No novelty claim is made by this architecture note. Its purpose is to expose the complete system boundary, identify reusable foundations, and state the exact missing proof obligations.
